# ADR-0014: Credit Ledger, Wallets, and Atomic Campaign Debit

- **Status**: Proposed
- **Context**: CR-2026-11 replaces campaign packages with prepaid credits. Partners buy credits (fiat × CPP), hold them in a wallet created at partner registration with `MAIN`, `BONUS`, and `PARTNER` accounts, and every campaign creation debits a configured amount of credits. Credit and debit operations must be atomic, idempotent, auditable, and never produce a negative balance, including under concurrent requests and duplicated webhooks.
- **Decision**: Create a new **Ledger** bounded context (`com.pawmotionai.ledger`) owning `Wallet`, `LedgerAccount`, and append-only `LedgerEntry`. All balance changes go through a single inbound port `PostLedgerEntryUseCase` (`credit`/`debit`) that, in one PostgreSQL transaction, locks the account rows (`SELECT ... FOR UPDATE`, i.e. pessimistic locking), validates the balance, inserts the entry with `balanceAfter`, and updates the cached balance. **In addition to pessimistic locking, optimistic locking is mandatory**: every JPA entity of the Ledger and Billing contexts (`WalletJpaEntity`, `LedgerAccountJpaEntity`, `PaymentTransactionJpaEntity`) and the `PartnerCampaignJpaEntity` declares a `@Version private Long version;` property (backed by a `version BIGINT NOT NULL DEFAULT 0` column), so every update is issued as `UPDATE ... WHERE id = ? AND version = ?`. Pessimistic locks serialize concurrent postings on the same account; the version check detects any lost update that bypasses the lock (stale detached entities, write paths that do not lock such as wallet blocking or account closing, or code regressions). A version conflict (`OptimisticLockException` / `ObjectOptimisticLockingFailureException`) rolls back the whole transaction, so no entry is persisted, and the use case retries up to 3 times with a fresh read (idempotency keys make the retry safe) before returning `409 Conflict`. Debits follow the account order `MAIN` → `BONUS` → `PARTNER` (accounts locked in that fixed order to avoid deadlocks) and are split across accounts when one balance is insufficient. Postings are idempotent through a unique key on `(account_id, reference_type, reference_id, direction)` (so a split campaign debit or refund produces one entry per account under the same reference) and a `CHECK (balance >= 0)` constraint is the last line of defense. Credits are `BIGINT`; fiat amounts are `NUMERIC(19,4)`. Campaign creation (Partner) and the debit (Ledger) execute in the **same local transaction**, orchestrated by the Partner application service calling the Ledger inbound port; payment confirmation (Billing) and the credit (Ledger) follow the same pattern. Cross-context facts (`CreditsPurchased.v1`, `CampaignCreditsDebited.v1`) are written to the outbox in that transaction.
- **Alternatives**: (1) Mutable balance column without entries — rejected, not auditable. (2) Full double-entry with platform counter-accounts — deferred; single-sided entries with references are sufficient for the MVP and can be extended with a `PLATFORM_REVENUE` account later. (3) Saga with reservation/commit across contexts — rejected for the monolith; higher complexity with no benefit while contexts share one database. (4) Optimistic locking only — rejected: hot accounts would retry often. (5) Pessimistic locking only — rejected: it does not protect write paths that skip the lock or use stale entities; both are combined.
- **Rationale**: Append-only entries give a complete audit trail and allow balance recomputation; row locks plus `@Version` checks plus DB constraints guarantee atomicity and non-negative balances; idempotency keys make retries and duplicated webhooks safe.
- **Positive consequences**: Provable consistency, simple statements, easy reconciliation, future features (bonus credits, refunds, other paid features) reuse the same postings.
- **Negative consequences**: This is a documented exception to "one context per transaction" (software-architecture.md); Partner and Billing depend synchronously on the Ledger port.
- **Risks**: Lock contention on a single busy account (low for MVP volumes); configuration drift between `CAMPAIGN_PRICE_AMOUNT`, `CAMPAIGN_CREATION_COST_CREDITS`, and CPP — mitigated by startup validation, warnings, and snapshotting the values used on each transaction/campaign.
- **Implementation guidance**: Tables `ledger_wallets`, `ledger_accounts`, `ledger_entries` (see data-architecture.md). `InsufficientCreditsException` maps to `402` Problem Details with `requiredCredits` and `balance`. Pricing binds to a validated `@ConfigurationProperties` record (`app.billing.*`, `app.campaign.*`). Every ledger/billing table has a `version BIGINT NOT NULL DEFAULT 0` column mapped with `jakarta.persistence.Version`; repositories that post use `@Lock(LockModeType.PESSIMISTIC_WRITE)` (with a lock timeout) to load accounts. Ledger entries are insert-only and do not need `@Version`. Concurrency tests with Testcontainers are mandatory and must cover parallel debits on the same account, a stale-version update failing, and retry without double posting.
- **Migration/reversal**: If contexts are extracted to services, replace the shared transaction with a reserve → confirm/release saga on the Ledger API, keeping entry idempotency keys unchanged.
