# ADR-0018: Live GPS Tracking and Strava Publication

- **Status**: Proposed
- **Context**: The mobile Home needs a Strava-like quick-start button to track a walk live, and owners want to publish activities to Strava. Activities currently only store manual duration/distance.
- **Decision**: Mobile tracking uses `expo-location` (foreground watch plus a **required** background location task via `expo-task-manager`, Expo development build) with a local tracking state machine (`IDLE → TRACKING ⇄ PAUSED → REVIEW → SAVED|DISCARDED`), point filtering by accuracy/speed, and local persistence (SQLite/file storage) of every point and finished activity as GeoJSON until the backend and Strava acknowledge it (offline queue with retry). The app prompts the owner to connect Strava on first tracking. The backend accepts an optional GeoJSON `Feature<LineString>` route on `POST /api/activities`, stores it as GeoJSON in `activity_routes.geojson JSONB` (PostGIS conversion deferred; maps render the GeoJSON directly), and records `source = LIVE_TRACKING`. Strava is a new **Integration** context behind `StravaPort`: OAuth 2.0 (`activity:write`), encrypted tokens, and asynchronous publication through the outbox (ADR-0006) — GPX upload when a route exists, manual activity otherwise — with retry/backoff honoring Strava rate-limit headers.
- **Alternatives**: Read activities from Strava instead of tracking in-app (rejected: does not satisfy quick-start tracking); synchronous Strava call on save (rejected: couples save to a third party); storing raw full-resolution points only (rejected: size, privacy).
- **Rationale**: In-app tracking owns the core data; Strava stays an optional, failure-isolated sink.
- **Positive consequences**: Rich activities with maps, better AI insights, social reach through Strava.
- **Negative consequences**: Background location requires a development build and platform permission review; Strava app registration and token management add operational work.
- **Risks**: Battery usage, GPS noise, Strava API limits/terms changes; mitigated by sampling configuration, filtering, and feature flag `STRAVA_ENABLED`.
- **Implementation guidance**: Proposed defaults pending confirmation: auto-publish on after connecting; `sport_type` mapping `WALK→Walk`, `RUN→Run`, `HIKE→Hike`, `BIKE_RIDE→Ride`, `SWIM→Swim`, `PLAY→Workout`. Secrets `STRAVA_CLIENT_ID`, `STRAVA_CLIENT_SECRET`, `STRAVA_REDIRECT_URI`, `INTEGRATION_TOKEN_ENCRYPTION_KEY` from environment only. Publication status persisted in `strava_publications`; idempotent by activity id.
- **Migration/reversal**: Additional sinks (Google Fit, Apple Health) become new adapters of the same publication port.
