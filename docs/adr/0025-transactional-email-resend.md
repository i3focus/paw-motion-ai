# ADR-0025: Transactional Email via Resend (Welcome Emails for Tutors and Partners)

- **Status**: Accepted
- **Context**: The notification module covers in-app notifications and Expo push (D-014), but there is no email channel. Account onboarding needs one: a welcome email when a pet tutor (`OWNER`) registers and when a partner (`PARTNER`) registers. Requirements: provider-agnostic port (consistent with `PaymentGatewayPort`/`PushGatewayPort` precedent), HTML + plain-text bodies (many clients score HTML-only mail as spam), no delivery guarantee strong enough to justify blocking registration, and no extra infrastructure in the Docker Compose dev environment.
- **Decision**: **Resend** (`https://api.resend.com`) is the transactional email provider, behind a new `EmailSenderPort` in the notification bounded context. `ResendEmailSender` posts `POST /emails` with a Bearer API key via `RestClient` (same adapter shape as `AbacatePayHostedCheckoutAdapter`); the `@Primary EmailGateway` selects Resend only when `MAIL_ENABLED=true` and `RESEND_API_KEY` is set, otherwise it delegates to `LoggingEmailSender` (stub, same pattern as `ExpoPushGateway`/`LoggingPushGateway`). Templates are classpath resources (`templates/email/welcome-tutor.html`, `welcome-partner.html`) branded with the design tokens (teal `#0F5C5C`, coral `#FF6B57`, cream `#FFF8EF`, Nunito), rendered by `WelcomeEmailTemplates` with `{{placeholder}}` substitution; every user-controlled value is HTML-escaped before interpolation. The notification module exposes the inbound port `SendWelcomeEmailUseCase` (`sendTutorWelcome`, `sendPartnerWelcome`), consumed by `RegisterOwnerService` and `RegisterPartnerService` — the same cross-module call convention already used for `EnsureWalletUseCase`. `WelcomeEmailService` wraps the send in `runCatching`: provider failures are logged as warnings and never propagate, so a broken mail provider cannot roll back account registration. Configuration lives under `app.mail.*` (`MAIL_ENABLED`, `RESEND_API_KEY`, `RESEND_FROM_EMAIL`, `RESEND_BASE_URL`, `APP_BASE_URL`, `PARTNER_PORTAL_BASE_URL`, `SUPPORT_EMAIL`). The Resend MCP server (`https://mcp.resend.com/mcp`) is registered in `.devin/mcp_config.json` with the API key injected via `${env:RESEND_API_KEY}` so agents can send/preview templates without new code.
- **Alternatives**: SMTP via `spring-boot-starter-mail`/JavaMail (rejected: needs an SMTP relay, TLS/session management and no delivery analytics); AWS SES (rejected for now: requires AWS account, sandbox exit and domain verification; plausible future adapter); the `com.resend:resend-java` SDK (rejected: `RestClient` + one POST endpoint keeps the adapter ~60 lines and consistent with the existing AbacatePay adapter; no new dependency); a full template engine like Thymeleaf/Freemarker or React Email (deferred: two `{{placeholder}}` templates don't justify the dependency; upgrade when templates grow); sending after commit via outbox/`@TransactionalEventListener` (deferred: welcome emails are best-effort; a durable outbox belongs with the events work in ADR-0005).
- **Rationale**: One synchronous `POST /emails` call inside the registration transaction is the simplest correct MVP: Resend queues the message server-side, failures are isolated from the transaction, and the port keeps provider swap cost at one adapter. Classpath templates ship inside the jar, render with zero dependencies, and escaping is owned by the renderer.
- **Positive consequences**: Welcome emails for both registration paths; email works out of the box in dev (`MAIL_ENABLED` + key in `.env`, logging stub otherwise); tests cover template escaping, the HTTP contract (local `HttpServer`) and failure isolation; the MCP config lets agents send previews on demand.
- **Negative consequences**: The send is synchronous inside the registration transaction — a slow Resend adds latency (mitigated by RestClient defaults; move to `@Async`/outbox if p95 registration time grows). API key is send-only: delivery status must be read in the Resend dashboard, not the API. The free/trial setup sends only to the Resend account email until `i3pet.com.br` is domain-verified.
- **Risks**: Unverified sender domain → mail lands in spam (verify `i3pet.com.br` DKIM/SPF in Resend before launch); template injection via `displayName` (mitigated by renderer escaping + test); provider outage (swallowed, logged — acceptable for welcome mail); secret leakage (key only in `.env`/env vars, never logged; `EmailGateway` does not log the auth header).
- **Implementation guidance**: `OutboundEmail(to, subject, html, text)` — plain text is always required alongside HTML. New emails render through `WelcomeEmailTemplates`-style components and go out via `EmailSenderPort`; do not call `ResendEmailSender` directly from use cases. Keep `MAIL_ENABLED=false` in CI/test profiles. For bulk/marketing mail use Resend broadcasts through the MCP, not this port.
- **Migration/reversal**: Swap `ResendEmailSender` for an SES/SMTP adapter implementing `EmailSenderPort`; callers, templates and the fallback stub are unaffected. Removing email entirely means deleting the `EmailGateway` delegate choice — `LoggingEmailSender` becomes the only sender.
