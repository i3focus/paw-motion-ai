# ADR-0015: Payment Gateway (AbacatePay Hosted Checkout) and Payment Transaction Lifecycle

- **Status**: Proposed
- **Context**: Partners pay in BRL (PIX and card) to obtain credits; credits must be granted only after a confirmed payment. Decision (2026-11-10): the provider is **AbacatePay** (https://docs.abacatepay.com). Relevant facts from its documentation: REST API `https://api.abacatepay.com/v2` with Bearer API keys (`abc_dev_…` = Modo Teste with simulated payments, `abc_prod_…` = production; permissions fixed per key); amounts in cents; responses `{ data, success, error }`; rate limit 100 req/s per store. The **checkout** (`POST /checkouts/create`) is a hosted page for one payment (PIX, card, boleto, Apple/Google Pay; default PIX + card), charges registered products (`items[].id` = product `id` or `externalId`, total ≥ R$ 1,00), is idempotent by `externalId`, has no expiry itself (`PENDING` until paid; inner PIX/boleto expire), supports `completionUrl`/`returnUrl`/`metadata`/`customerId`, and has statuses `PENDING → PAID | REDEEMED`, `PAID → UNDER_DISPUTE | REFUNDED`, `UNDER_DISPUTE → PAID | REFUNDED`. Webhooks v2 send `checkout.completed`, `checkout.refunded`, `checkout.disputed`, `checkout.lost` in an envelope `{ id, event, devMode, data }`; each delivery carries the configured secret (`X-Webhook-Secret` header / `webhookSecret` query) and an `X-Webhook-Signature` (base64 HMAC-SHA256 of the raw body with AbacatePay's public key); non-2xx responses are retried up to 7 times over ~18 h, `2xx` must come within 30 s, and retries keep the same `id`. The transparent checkout (`POST /transparents/create`, arbitrary `amount`, `transparent.*` events) needs a custom UI and card tokenization via abacatepay.js.
- **Decision**: Create a **Billing** bounded context (`com.pawmotionai.billing`) owning `PaymentTransaction` with states `PENDING → CONFIRMED | FAILED | EXPIRED | CANCELED`, `CONFIRMED → DISPUTED | REFUNDED`, `DISPUTED → CONFIRMED | REFUNDED`. Providers sit behind `PaymentGatewayPort` (`createCheckout`, `fetchCheckout`, `deleteCheckout`, `verifyWebhook`). The MVP adapter is `AbacatePayHostedCheckoutAdapter` (`PAYMENT_PROVIDER=abacatepay`): one AbacatePay product `ABACATEPAY_CREDIT_PRODUCT_EXTERNAL_ID` priced at 100 cents (1 BRL) is created once per environment; a purchase of N BRL creates a checkout with `items=[{id: <product externalId>, quantity: N}]`, `methods=[PIX, CARD]`, `externalId=<transactionId>`, `metadata={partnerId, transactionId}`, `completionUrl`/`returnUrl` under `PARTNER_PORTAL_BASE_URL`, and optional `customerId` when the partner has a registered CPF/CNPJ. The partner is redirected to the returned `url`. Webhook `POST /api/webhooks/payments/abacatepay` verifies the secret (constant-time) and the HMAC signature, checks `devMode` against the environment, stores the event id for deduplication, re-fetches the checkout (`GET /checkouts/get`) as source of truth, and maps events: `checkout.completed` (`PAID`) → `CONFIRMED` + Ledger credit to `MAIN`; `checkout.disputed` → `DISPUTED` + wallet `BLOCKED` (dispute won → `CONFIRMED`); `checkout.refunded` / `checkout.lost` → `REFUNDED` + compensating debit (up to available balance) + partner blocked. Pending transactions older than `BILLING_PENDING_TTL` become `EXPIRED` and their checkout is deleted (`POST /checkouts/delete`). A deterministic `FakePaymentGatewayAdapter` (`PAYMENT_PROVIDER=fake`) is kept for CI.
- **Alternatives**: AbacatePay transparent checkout (deferred: arbitrary amounts and in-app UX, but requires custom PIX/card UI and abacatepay.js); AbacatePay payment link (rejected: multiple payments per link break one-transaction-per-checkout mapping); one product per purchase amount (rejected: product explosion); Stripe/Mercado Pago/Pagar.me (not chosen); client-side confirmation only (rejected: forgeable); storing card data (rejected: PCI scope).
- **Rationale**: Hosted checkout is the fastest way to accept PIX and card with no card data in our systems; the 1-BRL product with quantity supports any whole-BRL amount; `externalId` gives provider-side idempotency and a stable link to our transaction; webhook + re-fetch is the reliable pattern for asynchronous PIX.
- **Positive consequences**: PIX and card at launch, Modo Teste for demos (Simular Pagamento button), no PCI scope, provider can be swapped behind the port.
- **Negative consequences**: Only whole-BRL purchases; partner leaves the portal to pay; webhooks require a public HTTPS URL (tunnel when running on local Docker); production requires AbacatePay account verification.
- **Risks**: Webhook spoofing (mitigated by secret + HMAC + re-fetch); `devMode` events reaching production (rejected by environment check); per-store minimum amounts and allowed methods differ in production (validated at startup/purchase); maximum `quantity` per item not documented — verify in Modo Teste and cap `BILLING_MAX_PURCHASE_AMOUNT` accordingly.
- **Implementation guidance**: Store `cppSnapshot`, `amount` (cents), `currency`, `expectedCredits`, `targetAccountId` (MAIN), `providerCheckoutId` (`bill_…`), `providerCheckoutUrl`, `idempotencyKey`, `version` (`@Version`) on the transaction. Endpoints that start purchases require an `Idempotency-Key` header. API key needs only `CHECKOUT:CREATE`, `CHECKOUT:READ`, `CHECKOUT:DELETE` (plus `CUSTOMER:CREATE` if customers are registered and `PRODUCT:CREATE` for the one-off product setup). Secrets `ABACATEPAY_API_KEY`, `ABACATEPAY_WEBHOOK_SECRET` come from the environment only; never log the webhook URL with its query secret. The webhook handler responds `2xx` for duplicates and `401` for invalid secret/signature.
- **Migration/reversal**: Transparent checkout or another provider is a new adapter; switching does not change stored transactions or ledger entries.
